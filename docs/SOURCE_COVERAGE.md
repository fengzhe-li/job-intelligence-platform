# Source Coverage Audit (Phase 2.5, corrected and extended in Phase 2.6)

This document is the honest source of truth for what each job source actually does automatically, what it doesn't, and why. **A connector class existing in the codebase does not mean the source is "integrated"** — integrated means the system can discover current jobs from that source automatically, ingest them through the real pipeline, and visibly report failures or incomplete coverage. Manual import alone is not integration.

**Phase 2.6 added a structured, machine-readable version of this same information**: `src/jobintel/source_coverage.py` (per-source `automation_status`/`coverage_scope`/`manual_check_required`/`manual_check_reason`/`manual_import_supported`/`known_gaps`/`recommended_manual_action`, merged with live health data), queryable directly via the `coverage-today` CLI command. This document remains the full narrative audit; `coverage-today` is the live, always-current answer to "what do I need to check myself right now" so that answer never has to be remembered from documentation. See "Phase 2.6 Changes" below for exactly what was corrected and why.

## What changed this pass

- **`connectors.base.PartialFetchError`**: Greenhouse, Lever, Ashby, Workable, and SmartRecruiters now isolate failures per company/board/account/site instead of one broken identifier aborting the whole connector's refresh. A refresh with some failures is reported as `partial` (not `error`, not silently `live_api`), and the identifiers that failed are named. A failed identifier's jobs are never closed that cycle (see the closure invariant below).

## Closure invariant (Phase 3)

**Absence may only imply closure when the current observation is known to be a complete snapshot of the relevant source scope.**

- Every connector returns a `connectors.base.SourceSnapshot`: its payloads plus `complete_scopes`, the scopes (one Greenhouse board, Lever site, Ashby board, Workable account, SmartRecruiters company+country filter, Workday tenant/site, WTTJ official-API organization) whose *entire* current listing was observed. Each payload is tagged with its scope (`raw_payload["_closure_scope"]`).
- A scope is complete only if the fetch succeeded with a recognised response shape, pagination reached the real end (not a safety page cap), nothing was cut by the per-identifier `limit`, no keyword filter dropped a listed job, and (Workday) every listed posting's detail was fetched. Otherwise it is recorded in `incomplete_scopes` with the reason and shown in source health.
- `LocalJobStore.write_snapshot` marks an observation `DISAPPEARED` only if it is absent **and** its scope is in `complete_scopes`. `write_jobs` and `ingest_from_connectors` never infer closure. Observations whose scope can't be determined (manual imports, legacy SmartRecruiters records) are never closed by absence.
- Default is fail-closed: connectors that don't prove completeness (Adzuna search, Prospects category discovery, manual imports) report no complete scope and can never close anything. **Prospects is PARTIAL_COVERAGE and never closes jobs**: its jobs stay active until another signal (a direct-ATS closure or a passed deadline) says otherwise.
- A suspicious collapse (0 results, or <20% of the last healthy count) withholds closure for that cycle (`closure_withheld` in health).
- `query.limit` is applied **per identifier**. Previously it capped each connector family's combined output at 100, which silently dropped every job beyond the cap. That is why the pre-Phase-3 local store held exactly 100 Greenhouse and 100 Ashby observations.
- **`SmartRecruiters` pagination**: previously fetched only `offset=0` regardless of how many postings a company actually had. Now paginates up to `totalFound` (capped at 10 pages/company).
- **`last_synced` / `last_successful_jobs_seen` preservation**: a failed or partial refresh no longer blanks out when the source last actually succeeded -- previously the dashboard would show "Last synced: never" for a source that worked yesterday and merely failed today. This was a real, reproducible bug, not a hypothetical one (see `tests/test_source_health.py`).
- **Suspicious-zero-result detection**: a `live_api` (successful, no exception) refresh whose `jobs_seen` drops to 0, or below 20% of that source's last healthy count, is now flagged with an explicit `warning` on the health record rather than silently accepted as "0 new jobs" or (worse) triggering mass closure inference on a parser regression.
- **Deadline provenance** (`SourceObservation.deadline`, `Job.deadline_observations` / `.deadline_conflict` / `.earliest_deadline`): never invented, preserved per-source-observation so two sources stating different deadlines for the same vacancy are both retained and the conflict is visible, not silently resolved.
- **Trackr domain corrected** (`thetrackr.com` &rarr; `the-trackr.com` / `app.the-trackr.com`) -- the previous domain could never have validated a real Trackr URL.
- **Prospects live discovery connector** -- the first of the four graduate sources with genuine automated discovery, built on real schema.org JSON-LD structured data. Two real bugs were found and fixed only by testing this live against the real site, not by unit tests against fixtures: a strict-JSON parser rejecting the site's own (common, real-world, technically-invalid-but-browser-tolerated) literal newlines inside JSON-LD string values, and a location/title extraction bug (JSON-LD `address` can be a plain string or a `PostalAddress` object, and `jobLocation` can be a list of several `Place`s -- the original code only handled one shape).
- **`connectors.utils.fetch_text` / `extract_json_ld`**: new shared helpers, reusable for any future source that publishes schema.org `JobPosting` JSON-LD (a common, SEO-driven, non-hidden, non-authenticated data source worth checking first on any new job board).

## Company / ATS Discovery Coverage

**"Greenhouse supported" (and the same for Lever/Ashby/Workable/SmartRecruiters) means (b): only jobs from boards already known to and configured in `config/target_companies.json`, never (a) "all Greenhouse jobs everywhere."** There is no mechanism anywhere in this codebase that discovers a company's ATS from nothing -- every company must already be a registry entry with a `careers_url` before `ats-discover`/`ats-verify` can even attempt to identify which ATS it uses by probing that URL for known link patterns (`GREENHOUSE_PATTERNS`, `LEVER_PATTERNS`, etc. in `ats_discovery.py`).

Current registry state (Phase 2.7, `config/target_companies.json`, five-state classification via `src/jobintel/company_coverage.py` / `company-coverage-report`): **83 companies seeded -- 37 AUTO_VERIFIED (a live-verified working connector: 33 across Greenhouse/Lever/Ashby/Workable/SmartRecruiters + 4 on the new generic Workday connector), 0 PARTIAL_AUTOMATION, 39 MANUAL_REQUIRED (no reasonable automated path found, or deliberately excluded -- see Juniper/HPE below), 7 TEMPORARILY_FAILED (fetch failed this cycle, not individually confirmed permanent), 0 UNKNOWN.** Automatic verified coverage of this registry: 37/83 = 44.6%. Coverage of "all UK companies using Greenhouse/Lever/etc." is, at best, "the subset of ATS-using companies someone thought to add a careers URL for, and that URL was successfully probed." This is a structural limitation of the seed-list design, not a bug -- but the distinction matters and must never be blurred in how this project is described. **Never say "83 companies covered" -- only the 37 AUTO_VERIFIED are.**

**Phase 2.6 registry repair pass** -- three real bugs found and fixed in `ats_discovery.py`, all via live testing against the registry's actual companies, none caught by the existing mocked test suite:

1. **Bot-identifying User-Agent.** `_fetch_text` sent `User-Agent: jobintel-ats-discovery/0.1`, which a number of large corporate WAFs reject outright (basic UA-sniffing, not a genuine anti-bot/CAPTCHA challenge -- confirmed by curling the same URLs with a standard browser UA and getting HTTP 200). Fixed by switching to a realistic Chrome UA string. This is explicitly **not** the same thing as the Cloudflare managed-challenge bypass this project refuses to do for Gradcracker/Bright Network -- ordinary UA-sniffing WAF rules are a much weaker mechanism than a JS/managed challenge, and using a normal browser UA (already standard practice throughout this project's own research) is not evasion.
2. **Stale `ats_discovery_error` never cleared on success.** `discover_company_entry`'s "fetched fine, no ATS candidate found" branch, and `verify_company_entry`'s "no connector candidate" branch, both spread `{**entry, ...}` without clearing error/verification-metadata fields left over from a previous failed attempt -- so a company whose page had since become reachable still displayed an old, misleading error. This turned out to be the dominant effect: **36 of 83 entries carried a stale `ats_discovery_error` before the fix; 0 do after.** Fixed by explicitly clearing the relevant fields (`ats_discovery_error`, and on the verify side `jobs_available`/`ats_verification_error`/`verification_*`) whenever a fresh attempt supersedes them.
3. **Stale connector guess after a company migrates ATS provider.** Darktrace was manually confirmed (live) to have migrated to Workday (`myworkdayjobs.com`), which this project has no connector for -- but `discover_company_entry`'s "no candidate found" branch didn't clear the old `connector_type`/`connector_token`/`greenhouse_board_token` fields from a prior (now-wrong) guess, so `candidate_from_entry` would have kept trying to verify against the old provider forever. Fixed by clearing these fields in the same branch.

Phase 2.6 net result: 25 → 34 verified (Cleo's token corrected from `cleoai` to `cleo`, confirmed live with 6 real jobs, plus 8 more genuine WAF-UA-blocked companies now reachable and verified: 10x Banking, GoCardless, OakNorth, Octopus Energy, Paddle, Palantir, Primer, Thought Machine).

**Phase 2.7** individually investigated all 49 companies still unresolved after Phase 2.6 (see "Phase 2.7 Changes" above for the full method and findings) and added a generic Workday connector, taking verified count to 37 (Darktrace, Lloyds Banking Group, and London Stock Exchange Group added; Juniper Networks UK's Workday match found but deliberately not enabled -- see below). 3 stale `careers_url` values were repaired (ClearBank, Ocado Technology, Trainline). The remaining 46 unresolved companies are genuine: 39 MANUAL_REQUIRED (34 reachable with no supported-ATS pattern found and no reasonable automated path within a bounded investigation, 2 with a confirmed named bot-protection block -- Bloomberg, Confluent -- 2 with a confirmed site-wide Cloudflare challenge already counted under Gradcracker/Bright Network's own source rows, and 1 deliberately-excluded Workday match -- Juniper Networks UK) and 7 TEMPORARILY_FAILED (fetch failed this specific cycle; several of these exact companies -- NatWest Group, Dyson, Arista Networks UK -- were directly observed to succeed on one run and fail on another this session, confirmed transient rather than permanent).

No fully automated way to discover *new* companies using a given ATS from nothing (e.g. crawling Greenhouse's own directory, if one exists, or searching for `boards.greenhouse.io` sites at web scale) was implemented -- that remains a materially different, larger feature (a genuine web-scale discovery crawler). What Phase 2.7 DID add is the company-discovery-from-observation mechanism (see above): new companies are still found reactively, through jobs the system already sees via Prospects/Adzuna/manual sources, not proactively crawled -- but they no longer require a source-code change to enter the monitored registry. `ats-add`/`ats-import`/`company-discovery-promote` are all ways new companies enter the registry.

## Phase 2.7 Changes

- **Individually investigated all 49 previously-unresolved companies** (35 UNRESOLVED_NO_SUPPORTED_ATS_PATTERN_DETECTED + 13 FETCH_FAILED_THIS_CYCLE + Darktrace) via live re-fetching with signature scanning for Workday/SAP SuccessFactors/Oracle/iCIMS/Jobvite/Avature/Teamtailor/Personio/schema.org-JobPosting, plus manual follow-up on every remaining failure/block. Findings: 4 companies on Workday (see below), 1 on SAP SuccessFactors (BT Group, single company -- below the "multiple companies" threshold for a new connector, not built this pass), 1 on iCIMS (Arm, same reasoning), 1 on Avature (Virgin Media O2, same reasoning), 3 with simply stale `careers_url` values (repaired), 10 with a confirmed named bot-protection block (Cloudflare/Vercel/"are you a robot"/generic WAF "Access Denied"), and the remainder genuinely custom/fully client-rendered career search apps with no discoverable public structured endpoint within a bounded investigation.
- **New generic Workday connector** (`connectors/workday.py`, `WORKDAY_PATTERNS` in `ats_discovery.py`): uses the same public "CXS" endpoint a Workday-hosted careers site's own frontend calls to render listings/details -- not a private API, no auth required. Live-verified against **3 different real target-company tenants** (Darktrace: 72 jobs/27 UK; Lloyds Banking Group; London Stock Exchange Group), each with a genuinely different tenant/site naming scheme, confirming the token format (`{tenant}.{wdN}/{site}`) generalises correctly rather than being Darktrace-specific. A real bug was caught and fixed only by live testing: the detail-fetch URL was double-prefixing `/job/job/...` (Workday's own `externalPath` already includes the leading `/job/...` segment), which produced a 406 on every single detail fetch until fixed. Also live-confirmed Workday's own `total` field is unreliable past the first page of a session -- pagination stops on page-size, never on `total`.
- **A 4th Workday candidate (Juniper Networks UK) was found but deliberately NOT enabled**: its careers page now redirects to `hpe.wd5.myworkdayjobs.com` -- Juniper Networks was acquired by HPE and no longer has its own careers site. That tenant is HPE's entire global job board, not Juniper-scoped; enabling it as configured would have mislabelled thousands of unrelated HPE postings as "Juniper Networks UK". This is exactly the kind of superficial-coverage claim this phase was told not to make.
- **3 stale registry URLs repaired** with their real current careers URL, found live (ClearBank: `clear.bank/careers` → `clear.bank/join-clearbank`; Ocado Technology: → `careers.ocadogroup.com`; Trainline: `thetrainline.com/careers` (404) → `trainlinegroup.com/careers/en/`, a different domain entirely).
- **Flakiness directly observed, not assumed**: NatWest Group, Dyson, and Arista Networks UK were confirmed-blocked (named Cloudflare/WAF pages) on one fetch and then succeeded on a later fetch in this same session; Revolut, Tesco Technology, and Akamai showed the same pattern. This is direct evidence that a single failed HTTP request must not permanently classify a company as unsupported -- the new `company_coverage.py` module encodes this as `TEMPORARILY_FAILED`, distinct from a confirmed, reproducible block (`MANUAL_REQUIRED`).
- **New five-state company coverage classification** (`src/jobintel/company_coverage.py`, CLI `company-coverage-report`): AUTO_VERIFIED / PARTIAL_AUTOMATION / MANUAL_REQUIRED / TEMPORARILY_FAILED / UNKNOWN for all 83 companies, generated from live registry state plus this phase's individually-confirmed findings -- never "a connector exists" alone. Final tally: **37 AUTO_VERIFIED, 0 PARTIAL_AUTOMATION, 39 MANUAL_REQUIRED, 7 TEMPORARILY_FAILED, 0 UNKNOWN**.
- **New company-discovery-from-observation mechanism** (`company_discovery.py`, `storage/company_discovery_store.py`, CLI `company-discovery-scan`/`-list`/`-promote`): companies seen through non-registry-scoped sources (Prospects, Adzuna, manual imports) that aren't already in the registry are logged with full provenance (source, example job, and an auto-detected ATS suggestion when the application URL itself reveals one) and can be promoted into the registry as an ordinary config entry through the exact same `ats-add`-style pipeline -- the registry can now grow without a source-code change. Live-tested end-to-end against real Prospects data: 20 genuinely new companies discovered in one scan (Babcock, AWE, GCHQ, MI5, MI6, Sellafield Ltd, and others), one promoted successfully into a scratch registry copy.

## Deadline Safety

`SourceObservation.deadline` is `None` unless a source explicitly states one -- never inferred, never defaulted to "soon" or any placeholder. `Job.deadline_observations` exposes every source's stated deadline for a canonical job by source name; `Job.deadline_conflict` is `True` when two sources disagree, and `Job.earliest_deadline` reports the soonest one **without discarding the conflict signal** -- both values remain visible via `deadline_observations`. See `tests/test_source_health.py::DeadlineSafetyTests`.

Only Prospects (live) and the manual/discovery-import path (Trackr/Gradcracker/Bright Network/Prospects manual fallback) can currently supply a deadline -- none of Greenhouse/Lever/Ashby/Workable/SmartRecruiters/WTTJ/Adzuna's public APIs expose an application-deadline field.
